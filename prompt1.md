## ЗАДАЧА 1: ОПТИМИЗАЦИЯ СЕТИ И ХОЛОДНОГО СТАРТА

### 1.1. Ликвидация избыточного запроса `/api/about` на каждый F5
* **Проблема:** В `static/js/core.js` на этапе инициализации (`syncAppVersion()`) отправляется сетевой запрос к `/api/about`. Эндпоинт читает весь файл `app_info.txt` и возвращает JSON весом **53.4 КБ** с полной историей изменений (changelog) только ради строки версии `data.version`. При этом версия `{{ app_version }}` уже вшита в HTML-шаблон (`index.html: window.APP_VERSION`).
* **Что сделать:**
  1. В `static/js/core.js` удалить вызов `syncAppVersion()` при старте страницы. Брать версию приложения напрямую из `window.APP_VERSION` или переменной шаблона.
  2. Запрос к `/api/about` перевести в ленивый режим: вызывать его **только** при фактическом открытии модального окна «О сайте» (`openAboutModal()`).

### 1.2. Объединение запросов настроек (`/api/settings` и `/api/settings/language`)
* **Проблема:** На старте параллельно отправляются два независимых HTTP-запроса: `translations.js` запрашивает `/api/settings/language`, а `settings.js` — `/api/settings`. Оба обращаются к одной таблице `user_settings`, и `/api/settings` уже содержит ключ `language`.
* **Что сделать:**
  1. Читать сохранённый язык мгновенно из `localStorage` при синхронном старте страницы.
  2. Избавиться от дублирующего запроса `/api/settings/language`, используя данные из единого запроса настроек `/api/settings`.

### 1.3. Оптимизация загрузки словаря `translations.txt` (38 КБ)
* **Проблема:** Файл `translations.txt` скачивается и каждый раз построчно парсится регулярками в JavaScript.
* **Что сделать:**
  1. Добавить отправку заголовка `ETag` и поддержку `304 Not Modified` в роут `translations_txt` в `app.py`.
  2. Кэшировать распарсенный JSON в `localStorage` по хэшу версии, чтобы не выполнять построчный парсинг текстового файла при каждом обновлении страницы.

## ЗАДАЧА 2: ОПТИМИЗАЦИЯ БАЗЫ ДАННЫХ SQLITE И ПАМЯТИ

### 2.1. Устранение дисковых блокировок `PRAGMA journal_mode=WAL`
* **Файл:** `database.py`
* **Проблема:** В функции `get_connection()` на **каждое** обращение к базе выполняется `conn.execute("PRAGMA journal_mode=WAL")`. В SQLite режим WAL выставляется единожды и сохраняется в файле БД. Повторный вызов на каждый запрос захватывает эксклюзивную блокировку и нагружает диск.
* **Что сделать:**
  1. Оставить установку `PRAGMA journal_mode=WAL` только внутри функции `init_db()`.
  2. В `get_connection()` добавить высокопроизводительные прагмы:
     ```python
     conn.execute("PRAGMA synchronous = NORMAL;")
     conn.execute("PRAGMA cache_size = -64000;")  # 64 MB RAM кэш страниц
     conn.execute("PRAGMA temp_store = MEMORY;")
     conn.execute("PRAGMA foreign_keys = ON;")
     ```

### 2.2. Индексация и автоочистка кэша `api_cache`
* **Файл:** `database.py`
* **Проблема:** В таблице `api_cache` поиск просроченных записей `WHERE expires_at < ?` делает Full Table Scan. База `app.db` разрослась до 43+ МБ, так как старый кэш никогда не очищается.
* **Что сделать:**
  1. Добавить индекс в `init_db()`:
     ```sql
     CREATE INDEX IF NOT EXISTS idx_api_cache_expires ON api_cache(expires_at);
     ```
  2. Добавить фоновую или периодическую функцию очистки `DELETE FROM api_cache WHERE expires_at < ?`, запускаемую при старте или с интервалом раз в сутки.

### 2.3. Линейный поиск $O(N)$ в списках пользователя
* **Файлы:** `utils.py`, `routes/rates.py`
* **Проблема:** Функция `fetch_user_rate(target_id, target_type)` при проверке оценки для каждой карточки каталога/календаря/профиля делает линейный перебор `for item in cached["data"]`. Для 50 карточек на странице и списка в 500 аниме это 25 000 холостых итераций.
* **Что сделать:**
  1. Индексировать кэш списков в память в виде хэш-таблицы: `{ f"{type}_{target_id}": item }`.
  2. Сделать получение оценки мгновенным — за $O(1)$.

### 2.4. Утечки памяти в истории модалок (`anime.js`)
* **Файл:** `static/js/anime.js`
* **Проблема:** `window.modalStack.push({ html: body.innerHTML, ... })` сохраняет гигантские куски сырого DOM (со всеми iframe, плеерами и карточками) в массив JS. При переходах по 10 связанным тайтлам память забивается сотнями мегабайт неутилизированных DOM-фрагментов.
* **Что сделать:**
  1. Хранить в `modalStack` только легковесное состояние: `{ id, type, scrollTop }`.
  2. При нажатии «Назад» восстанавливать данные тайтла из существующего кэша `_animeDetailsCache`, не храня гигантский HTML в оперативной памяти.

## ЗАДАЧА 4: БЕРЕЖНЫЙ РЕДИЗАЙН И СВЕТЛАЯ ТЕМА (БЕЗ ЛОМКИ ИНТЕРФЕЙСА)

> **Главный ориентир:** Ничего не перекраивать! Все элементы, структура сетки, правый сайдбар и таблица должны остаться на 100% привычными и узнаваемыми. Проводится только визуальная шлифовка: исправление светлой темы, аккуратные радиусы скруглений и эстетичные тени.

### 4.1. Привязка `rates.css` к глобальной дизайн-системе
* **Файл:** `static/css/rates.css`
* **Проблема:** Все цвета в списках жестко захардкожены тёмными HEX-значениями (`#141418`, `#22222a`, `#1a1a20`, `#d0d0d8`, `#888899`). В светлой теме (`[data-theme="light"]`) списки остаются тёмными с грязными рамками.
* **Что сделать:**
  Заменить все захардкоженные цвета на CSS-переменные:
  - Фон карточек и сайдбара: `var(--card-bg)`
  - Границы и рамки: `var(--card-border)` и `var(--border-sub)`
  - Основной текст: `var(--text-main)`
  - Второстепенный текст: `var(--text-muted)`
  - Акцентный цвет (hover/активные фильтры): `var(--primary)`
  - Проверить идеальное отображение как в тёмной (`dark`), так и в светлой (`light`) теме.

### 4.2. Премиальный вид карточек в сетке списков (Cards View)
* **Файл:** `static/css/rates.css` (`.shiki-grid-card`, `.shiki-grid-poster-wrap`, `.shiki-grid-score`)
* **Что сделать:**
  1. **Скругления и форма:** Изменить устаревший `border-radius: 4px;` на современный мягкий радиус `12px` (или `14px`).
  2. **Микроанимации Hover:**
     - Добавить плавный подъем: `transform: translateY(-4px);`
     - Добавить мягкое неоновое свечение: `box-shadow: 0 10px 24px var(--shadow-glow);`
     - Добавить деликатный зум постера: `.shiki-grid-card:hover .shiki-grid-poster { transform: scale(1.04); }` (с `overflow: hidden; transition: transform 0.25s ease`).
  3. **Бейдж оценки (`.shiki-grid-score`):**
     - Заменить грубый непрозрачный прямоугольник на стеклянную капсулу:
       ```css
       background: rgba(0, 0, 0, 0.65);
       backdrop-filter: blur(8px);
       -webkit-backdrop-filter: blur(8px);
       border: 1px solid rgba(255, 215, 0, 0.3);
       border-radius: 8px;
       color: #ffd700;
       font-weight: 700;
       padding: 2px 6px;
       display: inline-flex;
       align-items: center;
       gap: 3px;
       ```
     - В разметке перед баллом выводить аккуратную иконку звезды `<i class="ti ti-star-filled"></i>`.

### 4.3. Устранение мёртвой зоны адаптивности (768px – 1200px)
* **Файл:** `static/css/main.css`, `static/css/rates.css`
* **Проблема:** `body { min-width: 1200px; }` в десктопном режиме ломает верстку на планшетах, маленьких ноутбуках и при разделении экрана в Windows (Split Screen / Snap 50/50 = 960px).
* **Что сделать:**
  1. Убрать жесткий `min-width: 1200px;` у `body`.
  2. Добавить адаптивную сетку с медиа-запросами для промежуточных разрешений (992px, 1100px):
     - На экранах < 1100px уменьшать ширину сайдбара списков с 250px до 200px или сворачивать второстепенные графики.
     - На экранах < 900px автоматически скрывать правый сайдбар и переносить фильтры в аккуратную выпадающую панель/шторку.

### 4.4. Модальное окно аниме на ультрашироких экранах (2K / 4K)
* **Файл:** `static/css/anime.css` (`.modal-content.anime-modal-content`)
* **Что сделать:**
  Добавить максимальную ширину и центрирование:
  ```css
  max-width: 1380px;
  margin: 0 auto;
  border-radius: var(--radius-card, 24px);
  ```
  Чтобы на больших мониторах модалка не растягивалась от края до края экрана, а сохраняла строгую журнальную композицию с читаемыми строками текста.
